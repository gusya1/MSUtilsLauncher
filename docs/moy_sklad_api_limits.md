# Лимиты JSON API МойСклада и поведение клиента

Источник ограничений: https://dev.moysklad.ru/doc/api/remap/1.2/#/restrictions (раздел «Ограничения»).

## Лимит запросов по способам аутентификации

Лимит «запросов за 3-секундный период» считается отдельно для каждого пользователя и решения; расход зависит от веса запроса (единиц лимита на HTTP-запрос).

| Аутентификация | Лимит |
|---|---|
| Токен пользователя (Bearer) — используется проектом (`MoySkladSettings.api_token`) | **15 запросов/3с** (вес 3, с 01.09.2026); с 01.12.2026 — **11 запросов/3с** (вес 4) |
| Токен публичного/приватного решения | 45 запросов/3с |
| Решение в статусе «Черновик»/«На модерации» | 11 запросов/3с |

Эндпоинты `GET /api/remap/1.2/report/stock/all` и `/report/stock/bystore`: вес 5 независимо от аутентификации (в проекте не используются).

## Параллельность и автоматическое отключение

- Параллельные запросы: ≤5 от одного пользователя или решения, ≤20 от аккаунта; превышение → HTTP 429 с кодом ошибки 1073.
- Автоматическое отключение доступа к API (восстановление — через поддержку МойСклада):
  - более 200 запросов с ошибкой 429 за минуту в течение последнего часа;
  - более 200 идентичных запросов, завершившихся ошибкой, за минуту в течение последнего часа;
  - более 100 PUT к одной и той же сущности за минуту в течение последнего часа.

## Прочие ограничения (не зависят от аутентификации)

- ≤8 КБ в заголовках запроса;
- ≤20 МБ тела запроса;
- ≤4 асинхронные задачи в очереди на аккаунт;
- обязательный gzip ответов (`Accept-Encoding: gzip` — клиент отправляет);
- ≤1000 элементов в массиве одного запроса (иначе HTTP 413).

## Заголовки остатка лимита

Ответы JSON API содержат заголовки: `X-RateLimit-Limit`, `X-RateLimit-Remaining` (лимит и остаток), `X-Lognex-Retry-TimeInterval` (мс), `X-Lognex-Reset` (мс, 0 если ограничение не установлено), `X-Lognex-Retry-After` (мс) — время ожидания перед повтором после HTTP 429.

## Поведение клиента

Ключевые классы и файлы: `MoySkladClient`, константы `DEFAULT_RATE_LIMIT_CALLS`/`DEFAULT_RATE_LIMIT_PERIOD`/`RATE_LIMIT_MAX_RETRIES`, функция `retry_delay_seconds` — `site/moy_sklad/client.py`; исключение `MoySkladRateLimitError` — `site/moy_sklad/exceptions.py`.

- Фиксированный лимитер: 11 запросов за 3 секунды, общий для всех методов клиента (`post`/`put`/`get_by_href`) — МойСклад считает лимит по токену, а не по методу (финальное значение для user-токена; до 01.12.2026, пока лимит 15 запросов/3с, клиент работает чуть медленнее, чем позволяет лимит). Лимитер in-memory, per-process: web и celery имеют отдельные «корзинки», хотя МойСклад считает лимит по токену глобально; при одновременной тяжёлой работе обоих процессов суммарно можно превысить лимит — закрывается retry по 429.
- HTTP 429: до 5 повторов на запрос; sleep = max(значение из заголовков `X-Lognex-Retry-After`/`X-Lognex-Reset` (мс), экспоненциальный backoff с джиттером). После исчерпания повторов — `MoySkladRateLimitError`. Повтор после 429 безопасен для всех методов, включая POST: запрос отклонён сервером по лимиту и не был обработан (в отличие от таймаута/обрыва соединения), поэтому дублей при повторе не возникает. Каждый повтор логируется WARNING (метод, URL, заголовки `X-RateLimit-Remaining`/`X-Lognex-*`, время сна), исчерпание повторов — ERROR; записи видны в `docker compose logs web`.
- Ретраи HTTP 500/503 — urllib3 Retry (10 повторов), отдельны от обработки 429.
- Проактивного троттлинга по `X-RateLimit-Remaining` нет; семафора на параллельные запросы нет.

## Конкурентность

Текущая конфигурация (`site/entrypoint.sh`): gunicorn ≤2 воркера + celery `-c 1` → максимум ~3 параллельных запроса к МойСкладу — под лимитом 5 от одного пользователя/решения. Конкурентность не поднимать выше: превышение ведёт к HTTP 429 (код 1073), а более 200 таких запросов за минуту — к автоматическому отключению доступа к API.

## Что клиентом не контролируется

Ограничения «≤1000 элементов в массиве» и «≤8 КБ заголовков» клиентом не проверяются — вызывающий код (`getters`, `creators`, `updaters`) их не нарушает.
