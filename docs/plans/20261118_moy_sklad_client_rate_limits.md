# План: адаптация MoySkladClient к новым ограничениям JSON API МойСклада

Дата: 2026-11-18
Статус: согласован, ожидает реализации
Исходник ограничений: https://dev.moysklad.ru/doc/api/remap/1.2/#/restrictions (раздел «Ограничения», актуально на 18.11.2026)

## Контекст

МойСклад изменил лимиты JSON API. Ключевые факты:

- Лимит «запросов за 3-секундный период» считается отдельно для каждого пользователя и решения; расход зависит от веса запроса (единиц лимита на HTTP-запрос).
- Для интеграций по логину/паролю или **токену пользователя** (то, что использует проект — `MoySkladSettings.api_token`, Bearer) вес растёт поэтапно:
  - с 12.05.2026: вес 2 → 22 запроса/3с;
  - с 01.09.2026: вес 3 → **15 запросов/3с** (актуально сейчас);
  - с 01.12.2026: вес 4 → **11 запросов/3с**.
- Токены публичных/приватных решений: 45 запросов/3с; решения в статусе «Черновик»/«На модерации»: 11 запросов/3с.
- Эндпоинты `GET /api/remap/1.2/report/stock/all` и `/report/stock/bystore`: вес 5 независимо от аутентификации (в проекте не используются).
- Параллельные запросы: ≤5 от одного пользователя или решения, ≤20 от аккаунта; превышение → HTTP 429 с кодом ошибки 1073.
- Остаток лимита отдаётся в заголовках ответа: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-Lognex-Retry-TimeInterval` (мс), `X-Lognex-Reset` (мс, 0 если ограничение не установлено), `X-Lognex-Retry-After` (мс).
- Автоматическое отключение доступа к API: более 200 запросов с ошибкой 429 за минуту в течение последнего часа; более 200 идентичных запросов, завершившихся ошибкой, за минуту в течение последнего часа; более 100 PUT к одной и той же сущности за минуту в течение последнего часа. Восстановление — через поддержку МойСклада.
- Прочие ограничения (не зависят от аутентификации): ≤8 КБ в заголовках запроса, ≤20 МБ тела запроса, ≤4 асинхронных задач в очереди на аккаунт, обязательный gzip ответов (`Accept-Encoding: gzip`), ≤1000 элементов в массиве одного запроса (иначе 413).

## Текущее состояние клиента (`site/moy_sklad/client.py`)

- `rate_limited(calls=45, period=3)` на `post`, `put`, `get_by_href` — старый лимит; для user-токена завышен втрое (сейчас) и вчетверо (с 01.12.2026).
- HTTP 429 не обрабатывается: urllib3 `Retry(total=10, status_forcelist=[500, 503])` ретраит только 500/503; response с 429 уходит вызывающему коду и падает в `getters.raise_for_status()` как обычный HTTPError.
- Заголовки остатка лимита не читаются.
- Лимитер `ratelimit` — in-memory, на процесс; экземпляры клиента внутри процесса его делят.
- gzip заголовок уже отправляется (`Accept-Encoding: gzip`) ✓.

## Согласованные решения

1. Заложить финальное значение лимита **11 запросов/3с** константой с комментарием о расписании изменения веса — безопасно на оба периода (до 01.12.2026 просто чуть медленнее).
2. При HTTP 429 — ограниченный retry внутри клиента: до **5 повторов** на запрос; sleep = max(значение из заголовков `X-Lognex-Retry-After` / `X-Lognex-Reset`, мс) и экспоненциального backoff с джиттером. После исчерпания повторов — бросать новое исключение `MoySkladRateLimitError`. Ограниченность критична: >200 запросов с 429 за минуту ведут к автоматическому отключению API.
3. Лимитер остаётся per-process (in-memory). Фактическая конкурентность низкая (gunicorn ≤2 воркера + celery `-c 1` → максимум ~3 параллельных запроса < лимита 5); страховка — retry по 429.
4. Проактивного троттлинга по `X-RateLimit-Remaining` не делать; семафора на параллельные запросы не добавлять (риск зафиксировать документально).
5. Скоуп: только `site/moy_sklad/client.py` и `site/moy_sklad/exceptions.py`. Вызывающий код (`getters`, `creators`, `updaters`, views, tasks) не меняется; сигнатуры методов клиента сохраняются.
6. Добавить юнит-тесты нового поведения в `site/moy_sklad/tests.py` (файла нет).
7. Написать документацию в каталоге `docs/` (сейчас там только `plans/`) про лимиты JSON API МС и поведение клиента.

## Реализация

### 1. `site/moy_sklad/exceptions.py`

- Добавить `MoySkladRateLimitError(MoySkladError)` — «лимит запросов МойСклада исчерпан после N повторов».

### 2. `site/moy_sklad/client.py`

- Константа лимита: `calls=11, period=3` (по умолчанию в `rate_limited`) с комментарием про расписание изменения веса запроса для user-токена (01.09.2026 → 15/3с, 01.12.2026 → 11/3с).
- Обработка 429 в `post`, `put`, `get_by_href`:
  - при `response.status_code == 429` — повтор запроса до 5 раз;
  - sleep = max(заголовок `X-Lognex-Retry-After` или `X-Lognex-Reset` (мс, делить на 1000) и экспоненциальный backoff с джиттером);
  - после исчерпания повторов — raise `MoySkladRateLimitError`;
  - повтор после 429 безопасен для всех методов, включая `post`: 429 означает, что запрос отклонён сервером по лимиту и не был обработан (в отличие от таймаута/обрыва соединения, где обработка могла начаться), поэтому дублей при повторе не возникает.
- Не менять: urllib3 Retry для 500/503, заголовки авторизации/gzip, сигнатуры методов.

### 3. `site/moy_sklad/tests.py` (новый файл)

Юнит-тесты без сети, mock'нутая session:
- 429 с заголовками `X-Lognex-Retry-After`/`X-Lognex-Reset` → повтор по заголовку;
- исчерпание повторов → `MoySkladRateLimitError`;
- rate limit на фиксированном окне (11/3с);
- отсутствие retry при 200 и 5xx.

## Актуализация документации

- Написать в `docs/` документ про лимиты JSON API МойСклада (по способам аутентификации, веса запросов, заголовки остатка лимита, автоматическое отключение) и поведение клиента: фиксированный лимитер 11/3с, retry по 429; текущая конфигурация (gunicorn ≤2 + celery `-c 1`) даёт максимум ~3 параллельных запроса — под лимитом 5, конкурентность не поднимать выше.
- Документация описывает только фактическое состояние репозитория; история изменений — в этом файле плана.

## Риски и что не делаем

- Per-process лимитер: web и celery имеют отдельные «корзинки», хотя МС считает лимит по токену глобально. При одновременной тяжёлой работе обоих процессов суммарно можно превысить лимит — закрывается retry по 429; при росте нагрузки вернуться к общему (redis) лимитеру.
- Проактивное троттлинг по `X-RateLimit-Remaining` не делаем: фиксированное окно + retry по 429 покрывают задачу; добавить позже, если появятся реальные 429.
- Семафор на параллельные запросы не добавляем: текущая конфигурация (≤3) под лимитом 5; риск зафиксирован в документации.
- Ограничения «1000 элементов в массиве» и «8 КБ заголовков» клиентом не контролируются — вызывающий код их не нарушает, фиксируется документально.
